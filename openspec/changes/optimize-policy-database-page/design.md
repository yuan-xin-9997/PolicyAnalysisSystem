## Context

政策列表当前通过 `GET /api/v1/policies` 提供分页、发布部门/类别/来源筛选和两个时间字段排序。前端把发布部门、类别 ID、来源 ID 都显示成自由输入框；`keyword` 在后端实际上同时匹配标题和正文，其中三字及以上使用现有 SQLite FTS5 trigram 索引，短词使用参数化 `LIKE`。政策详情将纯文本正文放在 `<pre>` 中，安全但阅读宽度、换行和信息层次较弱。

本变更跨越 FastAPI 查询契约、SQLAlchemy 仓储、Vue 查询状态和页面样式。它必须继续使用 SQLite、保持分页与权限检查、使用北京时间展示时间，并避免把抓取到的正文解释为可信 HTML。

## Goals / Non-Goals

**Goals:**

- 让筛选控件只展示当前政策数据中实际可用的发布部门、类别和来源。
- 提供语义独立的标题关键词与正文全文检索，并复用现有 FTS5 能力。
- 清楚表达当前排序字段、排序方向以及切换行为。
- 在不降低内容安全性的前提下提升长篇政策正文的可读性。
- 保持查询条件可写入 URL，刷新、前进后退和分享链接后可恢复。

**Non-Goals:**

- 不实现搜索结果相关度排序、高亮、同义词、分词词典或跨字段高级查询语法。
- 不引入 Elasticsearch、PostgreSQL 或外部搜索服务，也不变更政策采集流程。
- 不把纯文本自动转换成 Markdown/HTML，不实现政策附件预览、批注或导出。
- 不在本变更中重新设计应用导航或其他业务页面。

## Decisions

### 1. 新增独立筛选元数据端点

新增受政策页面权限保护的 `GET /api/v1/policies/filters`，返回去重并稳定排序的 `publishers`、`categories` 和 `sources`。选项仅来源于至少一条现存政策记录：发布部门返回字符串，类别和来源复用 `{id, code, name}` 引用结构。路由必须放在 `/{policy_id}` 之前或使用不会被动态路由吞掉的声明方式。

选择独立端点而不是把选项塞进每次列表响应，是为了让元数据契约可独立缓存、测试和刷新，也避免分页查询重复携带相同数据。未采用前端从当前页聚合，因为当前页不能代表数据库完整可选范围；未复用来源管理接口，因为它可能包含尚无政策的来源和类别。

### 2. 将标题关键词和正文全文检索分为两个查询参数

保留 `keyword` 作为标题关键词参数，但将其查询范围收窄为标题；新增 `full_text` 专门查询 `content_text`。两个条件同时提供时使用 AND 组合，其他筛选条件继续参与 AND 组合。两者都进行长度、首尾空白和控制字符校验。

正文检索继续使用现有 FTS5 表：三字及以上使用参数化的字面短语 MATCH，少于三字使用转义后的参数化 `LIKE`。标题关键词使用转义后的包含匹配，从而符合用户对标题框的直观预期。未增加搜索模式选择器或查询语法，以控制复杂度和误用风险。

### 3. 筛选选项与 URL 查询状态分离管理

Vue 页面挂载时并行请求筛选元数据和政策列表。表单以 `<select>` 提供“全部”空值及数据库返回选项；类别和来源仍向列表 API 发送稳定 ID，发布部门发送规范字符串。`full_text` 与既有筛选项一起进入路由查询参数；清空筛选恢复默认排序和第一页。

筛选元数据加载失败时显示独立错误提示，避免把元数据错误误报成政策列表错误；已有 URL 中的有效值仍保留在表单状态，使列表查询不依赖选项请求成功。选择原生 select 是为了获得稳定的键盘和屏幕阅读器支持，暂不引入组件库或可搜索下拉框。

### 4. 排序状态同时使用可见文字、图标和语义属性表达

列表只允许按发布时间或最近抓取时间排序。当前列标题显示“升序（最早优先）”或“降序（最新优先）”以及方向图标，表头设置对应 `aria-sort`，按钮提供完整的下一步操作说明。点击当前列反转方向；点击另一列时默认降序。请求中的 `sort_by`、`sort_order` 和 API 返回值保持一致。

不只依赖箭头或颜色，因为这对首次使用者和辅助技术不够清楚；也不新增独立排序下拉框，以避免桌面表格上出现两套控制同一状态的入口。

### 5. 详情正文保持纯文本并采用语义化阅读布局

详情页把标题、来源/类别标识、核心元数据、原文操作和正文分成清晰区域。正文使用普通文本绑定，配合 `white-space: pre-wrap`、自动断词、适合中文阅读的行高和受限阅读宽度，保留采集文本中的换行且不执行 HTML。空白行由浏览器按纯文本换行展示，不进行不可靠的标题自动识别。

相比 `v-html`，该方案不会执行抓取内容中的标签或脚本；相比逐行生成大量 DOM 节点，它更简单并能忠实保留原文。移动端允许元数据和操作区域自然换行，长 URL 或无空格字符串不得撑破容器。

### 6. 测试围绕契约、查询组合与可访问交互分层

后端覆盖筛选选项仅来自已有政策、稳定排序、权限、参数校验、标题/正文范围差异、短词回退及组合查询。前端单元测试覆盖查询序列化/恢复、选项渲染、元数据失败、排序提示和正文纯文本渲染；端到端冒烟测试覆盖从筛选或全文检索进入详情的主路径。现有分页、北京时间和详情 404 行为作为回归测试继续保留。

## Risks / Trade-offs

- [筛选选项对大数据集执行去重查询，可能增加页面首次加载成本] → 为字段建立简洁的 DISTINCT/JOIN 查询并稳定排序，端点与列表并行加载；先用现有规模验证，只有出现证据时再增加缓存。
- [SQLite FTS5 trigram 对一至二字查询无索引加速] → 保留转义 LIKE 回退以保证中文短词正确性，并限制输入长度；在测试中覆盖字面 `%`、`_` 和引号。
- [`keyword` 从标题+正文改为仅标题会改变旧链接语义] → 前端新增明确的全文参数并更新文档；该项目暂无发布版 OpenSpec 契约，实施时用回归测试固定新语义。
- [数据库中的历史筛选值可能很多] → 首版使用原生下拉框以满足“提供可选项”的目标；若真实数据证明难以使用，再单独规划可搜索组合框。
- [原始正文换行质量取决于采集结果] → 忠实、安全地显示现有纯文本，不在展示层猜测文档结构；采集清洗属于独立变更。

## Migration Plan

1. 先增加后端响应模型、筛选元数据端点和新查询参数，并完成兼容现有数据的自动化测试。
2. 更新前端类型、查询状态、列表和详情样式，再运行后端、前端与端到端测试。
3. 更新 README、需求规格说明书、设计说明书和部署相关说明；本变更不修改生产 `config/app.json`。
4. 按现有 Jenkins 流程部署；由于没有数据库结构迁移，可通过回滚应用版本恢复。若回滚，带 `full_text` 的新链接会被旧后端拒绝，页面应随应用版本整体回滚。

## Open Questions

无。首版按原生下拉筛选、标题包含匹配、正文全文字面匹配和纯文本阅读布局实施；更高级检索或可搜索下拉框需基于实际数据量另行立项。
